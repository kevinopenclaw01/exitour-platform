# EXITour 프로젝트 기준 명세

## 플랫폼 개요

EXITour는 한국인 여행자를 위한 프리미엄 맞춤 여행 상담 플랫폼이다. 초기 단계에서는 목적지, 여행 상품, 계약 호텔, 맞춤 패키지, 견적 요청 UI를 제공하는 정적 홈페이지로 시작한다. 이후 Supabase/Postgres 기반 데이터 저장, 관리자 페이지, 가격 변경 승인 플로우, OpenClaw API 연동을 단계적으로 확장한다.

핵심 방향은 "정해진 패키지 판매"가 아니라 고객의 여행 조건에 맞춰 호텔, 차량, 투어, 현지 케어를 조합하는 여행 컨시어지 서비스다.

## 주요 목적지

1단계 MVP 기준 주요 목적지는 다음과 같다.

- 필리핀: 보라카이, 보홀, 세부
- 베트남: 다낭, 나트랑, 푸꾸옥, 사파, 하노이, 호치민, 달랏, 무이네
- 괌
- 두바이
- 카자흐스탄
- 유럽

목적지 데이터는 향후 도시, 국가, 시즌, 추천 대상, 대표 상품, 계약 호텔, SEO 메타데이터와 연결될 수 있어야 한다.

## 고객 대상

- 가족 단위 프리미엄 휴양 고객
- 허니문과 기념일 여행 고객
- 아이 또는 부모님 동반으로 동선 안정성이 중요한 고객
- 항공권은 직접 구매했지만 호텔, 차량, 투어 조합이 필요한 고객
- 자유여행 감각은 유지하되 현지 예약과 일정 품질은 전문가에게 맡기고 싶은 고객
- 동남아 휴양지, 괌, 두바이, 유럽 등에서 검증된 호텔과 서비스를 원하는 고객

## 사이트 목표

- EXITour 브랜드 신뢰 형성
- 주요 목적지와 상품, 호텔 특가를 한국어로 명확히 안내
- 상담 전 고객이 여행 방향과 예산을 정리할 수 있게 돕기
- 견적 요청으로 이어지는 전환 흐름 제공
- 향후 DB, 관리자 페이지, OpenClaw 연동이 쉬운 데이터 구조 유지
- 검색 엔진과 AI 답변 엔진이 이해하기 쉬운 콘텐츠 구조 확보

## 상품 구조

상품은 현지 서비스 단위로 분리한다. 각 상품은 목적지 범위, 카테고리, 기본 설명, 소요 시간, 시작 가격, 포함/강조 사항을 가진다.

초기 상품 유형:

- 공항 픽업
- 공항 샌딩
- 렌터카
- 호핑투어
- 스노클링
- 마사지
- 일일투어
- 맞춤 패키지

향후 DB에서는 상품 기본 정보와 가격 조건을 분리한다. 상품은 변하지 않는 설명과 운영 조건을 갖고, 가격은 시즌, 인원, 옵션, 환율, 마진 정책에 따라 별도 테이블에서 관리한다.

## 호텔 구조

호텔은 목적지와 연결되는 계약 숙소 단위로 관리한다. 각 호텔은 이름, 목적지, 등급, 설명, 시작가, 혜택, 이미지, 객실 타입, 계약 상태를 가질 수 있다.

향후 확장 필드:

- 호텔 기본 정보: 이름, 국가, 도시, 등급, 주소, 설명
- 객실 정보: 객실 타입, 기준 인원, 최대 인원, 조식 포함 여부
- 계약 정보: 공급가, 판매 가능 기간, 취소 규정, 특전
- 가격 정보: 날짜별 요금, 시즌 구간, 환율 기준, 마진율
- 운영 정보: 추천 대상, 픽업 가능 여부, 관리자 노출 여부

## 맞춤 패키지 구조

맞춤 패키지는 단일 상품이 아니라 여러 리소스를 조합하는 상담 결과물이다.

구성 요소:

- 목적지와 여행 기간
- 인원 구성: 성인, 아동, 유아
- 항공권 보유 여부
- 호텔 등급과 객실 타입
- 공항 이동
- 현지 차량 또는 렌터카
- 투어와 액티비티
- 마사지, 식사, 기념일 옵션
- 고객 예산과 선호 여행 속도

맞춤 패키지는 견적 요청, 상담 메모, 견적안, 승인 상태, 결제 상태로 이어지는 업무 흐름을 고려해 설계한다.

## 가격 DB 구조 방향

가격은 상품/호텔 본문 데이터에 직접 박아두지 않고 별도 가격 정책 데이터로 분리한다.

권장 방향:

- `destinations`: 국가, 도시, 슬러그, 설명, 추천 시즌
- `products`: 상품명, 카테고리, 목적지 범위, 설명
- `hotels`: 호텔명, 목적지, 등급, 설명, 계약 상태
- `hotel_rooms`: 호텔별 객실 타입과 기준 인원
- `price_rules`: 상품 또는 객실에 연결되는 가격 규칙
- `season_windows`: 성수기, 준성수기, 비수기 등 날짜 구간
- `exchange_rates`: 통화별 기준 환율과 적용일
- `margin_rules`: 카테고리별 또는 공급처별 마진 정책
- `quote_requests`: 고객 견적 요청 원문
- `quote_items`: 견적서에 포함된 호텔, 상품, 차량, 투어 항목
- `price_change_requests`: 가격 변경 승인 요청
- `audit_logs`: 관리자 변경 이력

가격 계산 로직은 처음부터 과하게 자동화하지 않는다. MVP에서는 관리자 검토와 승인 가능한 구조를 먼저 만든다.

## 시즌/환율/마진 기반 가격 정책

가격은 다음 요소를 조합해 산정한다.

- 기본 공급가
- 시즌 구간: 성수기, 준성수기, 비수기, 특정 연휴
- 환율: 공급 통화와 원화 기준 환율
- 마진: 상품군, 공급처, 목적지, 프로모션 여부에 따른 마진율 또는 고정 마진
- 인원 조건: 최소 출발 인원, 성인/아동/유아 구분
- 옵션 조건: 전용차, 프라이빗 투어, 객실 업그레이드, 식사 포함 여부

고객에게 표시되는 가격은 "시작가"와 "상담 후 확정"을 명확히 구분한다. 실제 확정 가격은 예약 가능 여부와 공급가 확인 후 관리자 승인 절차를 거친다.

## OpenClaw 가격 변경 승인 플로우

OpenClaw API가 가격 변경 제안을 만들 수 있더라도 실제 고객 노출 가격은 자동 반영하지 않는다.

목표 플로우:

1. OpenClaw 또는 내부 가격 계산기가 가격 변경안을 생성한다.
2. 변경안은 `price_change_requests`에 `pending` 상태로 저장된다.
3. 관리자가 기존 가격, 신규 가격, 변경 사유, 적용 기간, 예상 마진을 확인한다.
4. 관리자가 승인하면 실제 가격 테이블에 반영된다.
5. 반려하면 변경안은 보존하되 고객 노출에는 반영하지 않는다.
6. 모든 승인/반려/수정 기록은 감사 로그에 남긴다.

원칙: 가격 변경은 승인 플로우 없이 자동으로 고객 화면에 반영하지 않는다.

## 관리자 페이지 목표

관리자 페이지는 운영자가 상담과 가격을 관리하는 내부 도구다.

MVP 목표:

- 견적 요청 목록 확인
- 견적 요청 상세 확인
- 상담 상태 변경: 신규, 확인 중, 견적 발송, 예약 진행, 종료
- 고객 연락처와 카카오톡 ID 확인
- 관리자 메모 작성
- 상품, 호텔, 목적지 기본 데이터 확인

확장 목표:

- 상품/호텔 CRUD
- 가격 규칙 관리
- 시즌 구간 관리
- 가격 변경 승인/반려
- 견적서 생성
- 예약 상태와 결제 상태 관리
- 관리자 권한 분리
- 변경 이력 추적

## Supabase/Postgres 목표 스키마 요약

목표 스키마는 정적 MVP의 `lib/data.ts` 구조를 기반으로 점진적으로 이전한다.

주요 테이블 후보:

- `destinations`
- `products`
- `hotels`
- `hotel_rooms`
- `product_prices`
- `hotel_prices`
- `season_windows`
- `exchange_rates`
- `margin_rules`
- `quote_requests`
- `quote_request_services`
- `quotes`
- `quote_items`
- `price_change_requests`
- `admin_users`
- `audit_logs`

보안 원칙상 Supabase service role key는 서버 환경에서만 사용하고 클라이언트 번들에 노출하지 않는다. 클라이언트는 익명 키와 RLS 정책이 허용하는 범위에서만 접근한다.

## SEO/AEO/JSON-LD 목표

검색 엔진과 AI 답변 엔진이 EXITour의 목적지, 상품, 호텔, 상담 구조를 이해할 수 있도록 페이지별 구조화 데이터를 추가한다.

목표:

- 페이지별 고유 title, description
- 목적지별 상세 페이지 메타데이터
- 상품별 상세 페이지 메타데이터
- 호텔별 상세 페이지 메타데이터
- `Organization` JSON-LD
- 여행 상품에는 `Product` 또는 `Service` JSON-LD 검토
- FAQ에는 `FAQPage` JSON-LD 검토
- sitemap.xml과 robots.txt 고도화
- 한국어 검색 질의에 맞춘 자연스러운 본문 콘텐츠

## 외부 호텔/항공 API 확장 방향

외부 API는 바로 붙이지 않고 provider adapter 구조를 먼저 정의한다.

방향:

- 호텔 공급 API별 adapter 분리
- 항공 API별 adapter 분리
- 내부 공통 모델로 변환 후 저장 또는 캐시
- 공급처 응답 원문과 정규화 데이터를 구분
- API 장애 시 기존 캐시와 수동 견적 흐름 유지
- 가격 자동 반영은 관리자 승인 플로우를 통과한 뒤에만 적용

예시 구조:

- `providers/hotel/*`
- `providers/flight/*`
- `lib/pricing/*`
- `lib/normalizers/*`

## 보안 원칙

- Supabase service role key는 클라이언트에 절대 노출하지 않는다.
- 관리자 기능은 인증과 권한 검사를 통과한 사용자에게만 제공한다.
- 고객 개인정보는 필요한 항목만 수집한다.
- 견적 요청, 연락처, 카카오톡 ID는 공개 페이지에서 조회할 수 없게 한다.
- 가격 변경, 견적 발송, 예약 상태 변경은 감사 로그를 남긴다.
- 외부 API 키는 환경 변수로 관리한다.
- RLS 정책을 기본 전제로 설계한다.
- 승인 없는 자동 가격 변경을 금지한다.

## 운영 원칙

- 한 번에 전체 명세를 구현하지 않고 Phase 단위로 진행한다.
- 각 Phase는 빌드 가능한 상태로 마무리한다.
- 고객용 콘텐츠는 한국어로 작성한다.
- lorem ipsum, 빈 페이지, TODO만 남기는 구현을 금지한다.
- 정적 데이터는 DB 이전이 쉬운 구조로 작성한다.
- 가격과 개인정보 관련 기능은 보수적으로 설계한다.
- 외부 연동은 실패 가능성을 고려해 수동 운영 대안을 남긴다.
- 중요한 운영 변경은 문서와 코드가 함께 업데이트되어야 한다.
