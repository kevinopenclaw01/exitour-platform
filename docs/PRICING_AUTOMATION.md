# 요금 계산 자동화 1차

## 현재 구현 범위

수동 환율 스냅샷과 원가 항목으로 계산안을 만드는 내부 계산 엔진이다. 원가·환율·정책·계산 결과를 복사해 보관하고, 승인·반려 도메인 전환을 테스트한다. 실제 Supabase 저장, 관리자 인증/승인 화면, 실시간 환율 수집, 고객 판매가 반영은 아직 연결하지 않았다. 기존 견적 저장, 관리자 견적 상태, 상품 상세/JSON-LD와 표시 가격은 변경하지 않는다.

`lib/pricing/`는 내부 원가를 다루므로 고객 페이지/클라이언트 컴포넌트에서 가져오지 않는다. `approval.ts`는 Node의 암호화 모듈을 사용하는 서버/CLI 코드다. 순수 도메인 함수의 `actorId`는 로그인이나 권한 검사가 아니다. 실제 연결 시 인증된 서버 DAL과 DB 트랜잭션에서 권한을 확인해야 한다.

## 실행 방법

```powershell
npm.cmd run test:pricing
npm.cmd run pricing:preview
npm.cmd run pricing:preview -- --input C:\approved-input\pricing-input.json
```

기본 미리보기 입력은 `docs/examples/pricing-input.json`의 가상 데이터다. 실제 공급처 계약 원가나 현재 환율이 아니다. 기본 예시는 기준 시각을 고정해 재현 가능하게 하였으며 현재 유효한 운영 가격으로 취급하면 안 된다. 미리보기는 DB/파일에 가격을 저장하지 않고 계산 결과만 표준 출력으로 보여준다. `publicPrice`는 승인 전이므로 `null`이다.

검증은 설치된 TypeScript로 계산/승인 모듈만 임시 폴더에 컴파일한다. 의존성 설치나 프로젝트 설정 변경 없이 테스트 후 자체 임시 폴더를 정리한다.

## 단위와 계산 정책

| 항목 | 의미 |
| --- | --- |
| `amountMinor` | USD는 센트, KZT는 티인(각 1/100), KRW는 원 |
| `unit` | `per-person`은 인원수만큼, `per-group`은 그룹 전체 기준 |
| `quantity` | 해당 과금 단위의 개수. 박수·차량수 등은 입력 전에 확정 |
| `rateMicros` | 기준 통화 1단위당 KRW 환율 × 1,000,000 |
| `markupBps` | 원가 가산율. 2,000은 원가의 20%이며 판매가 대비 마진율과 다름 |
| `fixedFeeKrw` | 그룹 전체에 한 번만 더하는 고정 수수료 |
| `roundingKrw` | 1인 표시가격의 올림 단위 |

1. 각 원가 라인의 금액 × 수량 × 필요 인원을 계산하고 통화별 환율로 환산한다. 라인 합계에서 원 단위로 한 번 올린다.
2. 원가 합계를 기준으로 가산액을 올림 계산하고 그룹 고정 수수료를 더한다.
3. 총액을 인원으로 나눈 뒤 표시 단위로 올린다. 고객 결제 총액은 1인 표시가격 × 인원이다.
4. BigInt 정수 연산으로 계산하되 JSON 결과는 안전한 정수 `number`만 허용한다. 잘못된 값, 오버플로, 누락 환율은 오류로 처리한다.

예: 가상 USD 100/인, 4명, 가상 환율 1,400원, 원가 가산 20%, 그룹 수수료 10,000원, 1,000원 단위 올림이면 원가 560,000원, 계산 총액 682,000원, 1인 표시가격 171,000원, 결제 총액 684,000원이다. 실제 카자흐스탄 요금이 아니다.

## 환율 스냅샷

`source`, `baseCurrency`, `quoteCurrency`, `rateKind`, 관측/입력 시각과 유효기간을 저장한다. 이번에는 `source=manual`만 허용한다. 현금 살 때(`cash-buy`), 송금(`remittance`), 기준율(`reference`)을 섞지 않으며 상품 정책과 일치해야 한다. 미래 관측, 입력 순서 오류, 만료된 환율, 환율보다 긴 견적 유효기간을 거부한다.

원가표의 480 KZT/USD와 1,400 KRW/USD는 과거 문서상의 환율이다. 실시간 값으로 간주하지 않는다. 실제 공급처 지급 통화와 환전/송금 방식을 확인한 뒤 운영 정책을 결정한다. 향후 공식 API adapter가 가져온 값을 같은 스냅샷으로 변환하되, 원가 계산만 다시 하고 공개 가격은 자동 변경하지 않는다.

## 승인 흐름과 한계

`createPriceProposal` → `pending` → 명시적 승인 또는 반려로 진행한다. 스냅샷은 원본과 분리해 깊게 동결하고 SHA-256 지문으로 입력/계산 변경을 검출한다. 미검증 원가, 출처 누락, 유효기간 만료, 제출 후 수정된 계산안은 승인할 수 없다. 원가나 환율이 바뀌면 새 revision과 새 승인이 필요하다.

승인 후 공개 DTO는 상품/revision, 인원 조건, KRW 표시가, 유효기간만 제공한다. 원가, 환율, 마진, 공급처, 승인자 등은 포함하지 않는다. 승인된 스냅샷은 이후 환율 변경으로 재작성하지 않는다.

이 단계의 지문은 디지털 서명이 아니며 클라이언트가 조작한 객체의 권한을 증명하지 않는다. 도메인 함수만으로 실제 판매가를 승인하거나 발행하면 안 된다. 운영 적용 시 서버 인증, 관리자 권한, DB 저장 스냅샷 재조회, revision 비교, 트랜잭션, 감사 로그, 요청 멱등성을 함께 구현해야 한다. 현재 승인/반려 기록은 반환 객체 안에만 있으며 DB 감사 로그가 아니다.

## 첫 실제 상품 연결 전 확인

- 원가표 행과 상품 일정/박수/여행지의 정확한 대응
- 실제 지급 원가와 공급처 제안 판매가의 구분
- 최소 인원, 과금 단위, 호텔/식사/입장료/항공 포함 범위
- 적용 기간, 가이드 조건, 공급처 확인일과 계약 출처
- 원가 가산율 또는 판매가 대비 마진율 중 운영 정책 선택
- 환율 종류, 유효기간, 반올림 단위와 공개 가격 승인권자

기존 4박 6일 189만원과 차린캐년 29만원은 이전 검수 상태 그대로 미확인이다. 이번 계산 결과로 맞다고 확정하거나 교체하지 않는다.

## Supabase 연결 계획

홈페이지 전용 `exitour-platform` 프로젝트가 이미 존재하나 2026-10-13 조회 시 `INACTIVE`다. 기존 복구 또는 신규 홈페이지 전용 프로젝트 선택이 필요하다. 계정의 주식 데이터 삭제와 홈페이지 DB 활성화는 별개이므로, 복구/생성을 수행했다고 가정하지 않는다. `.env.local`과 키는 변경하거나 출력하지 않는다.

프로젝트 선택 이후 기존 스키마/테이블/권한을 먼저 조회하고, 승인 기능은 별도의 내부 스키마에 원가 라인, 환율 스냅샷, 요금 revision, 승인 감사 로그를 보관하는 방향으로 추가한다. 원가·계산 초안에는 `anon` 접근을 허용하지 않는다. 공개 영역에는 승인된 최소 DTO만 제공한다. 기존 quote 테이블과 RLS를 재생성하거나 삭제하지 않는다.

관련 공식 문서: [Supabase 프로젝트 복구](https://supabase.com/docs/guides/platform/upgrading#pause-and-restore), [사용자 정의 스키마](https://supabase.com/docs/guides/api/using-custom-schemas).

## 이후 순서

1. 홈페이지 DB 복구/신규 선택과 실제 원가 대응 확인

3. 상품 등록 폼 및 이미지 업로드를 초안 저장 방식으로 추가
4. 공식 환율 adapter와 재계산 대기열 연결
5. 영상 업로드·문서 추출은 결과 검토 후 발행하는 방식으로 추가
