# 아이디어 재판소

## 왜 재판인가

모델 하나에게 "내 아이디어 어때?"라고 물으면 칭찬과 무난한 조언이 섞인 답이 돌아온다. 재판은 이 문제를 구조로 푼다. 공격만 하는 검사, 방어만 하는 변호인, 양쪽을 다 의심하는 배심원, 그리고 결론을 공식에 묶어 두는 재판장. 역할마다 따로 서브에이전트를 띄우는 이유는, 한 모델이 검사와 변호인을 동시에 연기하면 논쟁이 서로 봐주는 쪽으로 무뎌지기 때문이다. 역할마다 모델을 다르게 지정할 수 있으면 한 모델의 버릇이 판결 전체를 끌고 가는 것도 막을 수 있다.

**피고는 아이디어이고, 공소사실은 "이 아이디어는 현재 형태로 실행하면 실패한다"이다.** 무죄는 "실행할 가치가 있다"는 뜻이다.

너(이 스킬을 실행하는 Claude)는 **서기**다. 사건을 접수하고, 법정을 구성하고, 역할들을 순서대로 소환하고, 집계 스크립트를 돌리고, 결과를 보고한다. 검사나 배심원의 일을 대신하지 않는다.

## 전체 흐름

```
0 법정 구성  모드·인원·역할별 모델 결정 → 구성표를 사용자에게 보여 줌 → 00-법정구성.json
1 사건 접수  서기(너)                         → 01-사건기록.md
2 공소 제기  검사                             → 02-공소장.md
3 답변       변호인                           → 03-답변서.md
4 증인 신문  증인 N명 (병렬)                  → 04-증언-N.md
5 최종 진술  검사·변호인 (병렬)               → 05-최종진술-검사.md / -변호인.md
6 배심 평결  배심원 N명 (병렬)                → 06-배심원-NN.json
  6b 평의    (심화 모드만) 익명 교차 검토 후 수정
7 평결 집계  scripts/verdict.mjs              → 07-평결집계.json
8 판결 선고  재판장                           → 08-판결문.md
9 보고      재판기록.md 합본 + 채팅 요약
```

각 역할은 사건 폴더의 앞 번호 파일을 읽고 자기 파일 하나를 쓴다. 기록을 파일로 주고받으면 배심원 12명에게 같은 긴 기록을 프롬프트로 12번 복사하지 않아도 되고, 재판이 끝나면 기록 전체가 디스크에 남는다.

## 0. 법정 구성

### 모드

| 모드 | 증인 | 최종 진술 | 배심원 | 평의 | 서브에이전트 호출 |
|---|---|---|---|---|---|
| 약식 | 0 | 없음 | 5 | 없음 | 8 |
| **정식** (기본) | 3 | 있음 | 12 | 없음 | 20 |
| 심화 | 3 | 있음 | 12 | 있음 | 32 |

사용자가 `약식`, `빠르게`, `간단히`라고 하면 약식, `심화`, `제대로`, `평의까지`라고 하면 심화다. `배심원수=3~12`, `증인수=0~5`로 인원만 바꿀 수도 있다.

### 역할별 모델 지정

사용자가 지정하지 않은 역할은 아래 기본값을 쓴다.

| 역할 | 기본 모델 | 이유 |
|---|---|---|
| 재판장 | `opus` | 전체 기록을 종합하는 판결문의 품질이 결과물의 가치를 좌우한다 |
| 검사 | `sonnet` | |
| 변호인 | `sonnet` | 검사와 같은 체급. 한쪽이 체급에서 밀리면 판결이 논리가 아니라 모델 차이로 갈린다 |
| 증인 | `sonnet` | |
| 배심원 | 홀수 번 `sonnet`, 짝수 번 `haiku` | 모델이 섞여야 표가 한 모델의 버릇으로 쏠리지 않는다 |

사용자가 지정하는 방식은 자유롭다. 다음을 모두 알아듣는다.

- `재판장=opus 검사=sonnet 변호인=sonnet 증인=haiku 배심원=haiku` — 역할 단위 지정 (`배심원=`은 배심원 전원)
- `배심원=opus:4,sonnet:4,haiku:4` — 혼합 배심. 페르소나 순서대로 **번갈아** 배정한다(opus, sonnet, haiku, opus, …). 한 모델에 투자자 페르소나만 몰리면 모델 비교가 페르소나 비교가 돼 버리기 때문이다.
- `배심원3=opus` — 개별 배심원 지정. 역할 단위 지정보다 우선한다.
- 자연어: "판사는 오퍼스, 나머지는 소넷으로", "배심원 전부 하이쿠" — 오퍼스=opus, 소넷=sonnet, 하이쿠=haiku. 판사=재판장, 변호사=변호인.
- 영어 역할명: judge, prosecutor, defense, witness, jury/juror.
- `기본`, `현재 모델`, `inherit` — 그 역할은 `model` 값을 생략해 세션 모델을 그대로 쓴다.

모델 값은 Agent 도구의 `model` 파라미터가 받는 값만 쓸 수 있다(보통 `opus`, `sonnet`, `haiku`이고 환경에 따라 더 있다 — 도구 스키마를 확인한다). 사용자가 GPT·Gemini·Grok 같은 다른 회사 모델을 지정하면, Claude Code의 서브에이전트로는 실행할 수 없다고 한 줄로 알리고 가장 가까운 Claude 모델로 대체한 뒤 구성표에 `요청: gpt-5 → 대체: sonnet`처럼 표시한다. 조용히 바꾸지 않는다.

### 배심원 페르소나 (순서대로 배정)

배심원이 N명이면 1번부터 N번까지 쓴다. 순서는 적은 인원에서도 고객·투자·재무·기술·마케팅 관점이 고르게 들어가도록 짜 놓았다.

| 번호 | 페르소나 | 이 사람이 보는 것 |
|---|---|---|
| 1 | 타깃 고객 | 사건기록의 핵심 고객 그 자체. "내가 이 돈을 낼까?" |
| 2 | 벤처캐피털 심사역 | 시장 규모와 10배 성장 가능성 |
| 3 | 재무 담당 임원(CFO) | 현금 흐름, 손익분기, 단위경제 |
| 4 | CTO 출신 엔지니어 | 기술적 실현 가능성과 구축·유지 비용 |
| 5 | 그로스 마케터 | 고객 획득 채널, 획득 비용, 전환율 |
| 6 | 회의적인 일반 소비자 | 상식선의 의심, 신뢰, "이거 사기 아니야?" |
| 7 | 연쇄 창업가 | 실행 속도와 첫 고객까지의 거리 |
| 8 | 법률·규제 자문 | 인허가, 개인정보, 책임 소재, 약관 |
| 9 | 보수적 엔젤투자자 | 원금을 잃을 위험, 최악의 시나리오 |
| 10 | 운영 전문가 | 현장 운영, 공급망, 고객 응대 부담 |
| 11 | 경쟁사 전략 담당 | "우리가 따라 하면 얼마나 걸릴까?" |
| 12 | 제품 디자이너(UX) | 첫 사용 경험과 습관화 |

1번 "타깃 고객"은 사건기록의 핵심 고객으로 구체화해서 넘긴다(예: "50대 초반, 연 1회 해외여행을 하는 맞벌이 부부").

### 증인 선정

서기가 사건의 성격에 맞춰 고른다. 기본 3명이면 **그 업종의 현업 실무자** 1명 + 아래에서 아이디어의 가장 큰 불확실성을 다룰 분야 2명이다.

시장조사 분석가 · 해당 업종 현업 실무자(업종을 구체적으로: "인바운드 여행사 운영 15년차") · 기술 아키텍트 · 재무·투자 심사역 · 법률·규제 전문가 · 마케팅·그로스 전문가 · 고객 리서처

### 구성표 고지

시작하기 전에 사용자에게 구성표를 보여 준다. 무엇에 몇 번의 호출이 드는지 알고 시작해야 하기 때문이다.

```
⚖️ 아이디어 재판소 — 정식 재판 (서브에이전트 20회 호출)
| 역할 | 인원 | 모델 |
| 재판장 | 1 | opus |
| 검사 | 1 | sonnet |
| 변호인 | 1 | sonnet |
| 증인 | 3 (여행업 실무자, 시장조사 분석가, 법률·규제 전문가) | sonnet |
| 배심원 | 12 | sonnet 6 · haiku 6 |
```

보여 준 뒤 바로 진행한다. 사용자가 "구성 먼저 보여줘"라고 했을 때만 확인을 기다린다.

## 1. 사건 접수

아이디어가 아예 없을 때만 묻는다. 한두 줄짜리 아이디어라도 되묻지 말고 빈칸을 `[가정]`으로 채워 접수한다. 서기가 채운 가정이 법정에서 공격받는 것 자체가 사용자에게 쓸모 있는 정보이고, 질문을 여러 번 주고받는 것보다 빠르다.

**사건 폴더**: 현재 작업 디렉터리의 `idea-court-cases/<YYYYMMDD>-<짧은-영문-슬러그>/`. 사용자가 `저장=<경로>`를 주면 그곳을 쓴다. 이후 서브에이전트에게는 **절대 경로**로 넘긴다.

**사건번호**: `<연도>-아이디어-<세 자리 순번>`. 순번은 `idea-court-cases/`에 이미 있는 폴더 수 + 1.

`01-사건기록.md`:

```markdown
# 사건기록 — <사건번호> 「<아이디어 이름>」

## 피고(아이디어) 요약
(세 문장)

## 핵심 고객
## 해결하려는 문제
## 해결 방식
## 수익 구조
## 진입 전략

## 제출된 자료
(사용자가 준 사실·숫자·링크 내용을 가능한 한 그대로. 해석하지 않는다)

## 서기의 가정
(사용자가 말하지 않아 서기가 채운 것. 항목마다 [가정] 표시)

## 공소사실
"이 아이디어는 현재 형태로 실행하면 실패한다."
```

사용자가 준 사실과 서기의 가정을 섞지 않는 이유: 법정은 무엇이 증거이고 무엇이 추측인지 알아야 판단할 수 있다.

`00-법정구성.json` (집계 스크립트가 페르소나와 모델을 여기서 읽는다):

```json
{
  "case_no": "2026-아이디어-001",
  "title": "아이디어 이름",
  "mode": "정식",
  "roles": {
    "judge": { "model": "opus" },
    "prosecutor": { "model": "sonnet" },
    "defense": { "model": "sonnet" },
    "witnesses": [{ "no": 1, "persona": "인바운드 여행사 운영 15년차", "model": "sonnet" }],
    "jurors": [{ "no": 1, "persona": "타깃 고객 — 50대 초반 맞벌이 부부", "model": "sonnet" }]
  }
}
```

세션 기본 모델을 쓰는 역할은 `"model": null`로 둔다.

## 2~8. 역할 소환

### 소환 방법

각 역할은 Agent 도구로 소환한다. `subagent_type`은 `general-purpose`, `model`은 구성표의 값(세션 기본이면 생략), `description`은 "검사: 공소장 작성"처럼 짧게. 프롬프트는 아래 틀을 따른다. `<SKILL_DIR>`은 이 스킬이 로드될 때 표시된 기본 디렉터리의 절대 경로다.

```
너는 AI 아이디어 재판소의 <역할>이다. <증인·배심원이면: 너의 페르소나: <페르소나> — <이 사람이 보는 것>>
<배심원이면: 너는 배심원 <번호>번이다.>

1. <SKILL_DIR>/references/roles.md 에서 "## 공통 법정 규칙"과 "## <역할 섹션 이름>" 섹션을 읽어라.
2. <배심원·평의·재판장이면: <SKILL_DIR>/references/rubric.md 를 읽어라.>
3. 사건 폴더 <CASE_DIR> 에서 다음 파일을 읽어라: <파일 목록>
4. 결과를 <CASE_DIR>/<출력 파일> 에 써라. 다른 파일은 수정하지 마라.
5. 다 쓰면 이 한 줄로만 답하라: "제출 완료: <출력 파일>"
```

배심원의 마지막 줄은 `"제출 완료: 06-배심원-NN.json, 표결 <GO/PIVOT/NO-GO>"`로 한다.

### 순서와 병렬

- **2 검사 → 3 변호인**은 순서대로. 변호인은 공소장을 읽어야 하므로 검사가 제출한 뒤에 소환한다.
- **4 증인**은 모두 한 메시지에서 동시에 소환한다.
- **5 최종 진술**은 검사와 변호인을 한 메시지에서 동시에 소환한다. 같은 모델 배정을 그대로 쓴다.
- **6 배심원**은 모두 한 메시지에서 동시에 소환한다. 서로의 평결표를 보지 못하게 하는 것이 독립 배심의 핵심이다.
- 다음 단계는 앞 단계의 결과에 의존하므로, 한 단계의 호출이 모두 끝난 뒤에 다음 단계로 간다.

약식 모드는 4·5단계를 건너뛰고, 배심원과 재판장이 읽을 파일 목록도 그에 맞춰 줄인다.

### 제출 확인

단계마다 출력 파일이 실제로 생겼는지 확인한다. 파일이 없거나 비어 있으면 같은 모델로 한 번 다시 소환한다. 그래도 실패하면 증인은 "불출석"으로 기록하고 넘어가고, 배심원은 결원으로 둔다(집계는 유효 평결표 3장 이상이면 진행된다). 결원과 불출석은 보고에 적는다.

### 6b. 평의 (심화 모드만)

1. 원래 평결표를 `06-배심원-NN.r0.json`으로 복사해 둔다.
2. `node <SKILL_DIR>/scripts/verdict.mjs <CASE_DIR> --brief` 를 실행해 `06b-평의자료.md`를 만든다. 이름·페르소나·모델을 지우고 순서를 섞은 요약이다. 누가 말했는지 보이면 "VC가 그렇게 말했으니까"나 "opus가 그렇게 봤으니까"로 표가 쏠린다.
3. 배심원 전원을 같은 페르소나·같은 모델로 다시 동시에 소환한다. roles.md의 "## 평의" 섹션을 읽고 자기 평결표를 덮어쓰게 한다.

### 7. 평결 집계

```
node <SKILL_DIR>/scripts/verdict.mjs <CASE_DIR>
```

점수를 직접 계산하지 않는다. 공식이 매번 똑같이 적용돼야 재판끼리 비교할 수 있다. 스크립트가 무효 평결표를 알려 주면 그 배심원을 한 번 다시 소환한 뒤 다시 집계한다. 공식의 자세한 내용은 `references/rubric.md`에 있다.

### 8. 판결 선고

재판장을 소환한다. 읽을 파일은 `00`~`05`의 모든 파일과 `07-평결집계.json`이다. 재판장은 집계된 주문을 그대로 선고하고, 다르게 본다면 보충의견에 적는다(roles.md "## 재판장").

## 9. 보고

1. `node <SKILL_DIR>/scripts/verdict.mjs <CASE_DIR> --bundle` 로 `재판기록.md` 합본을 만든다.
2. `08-판결문.md`를 읽고 채팅에 아래 형식으로 요약한다. 판결문 전체를 붙이지 않는다 — 파일에 있다.

```
⚖️ 사건 <사건번호> 「<아이디어 이름>」 — **<주문>**
최종 점수 <NN.N> / 100 · 표결 GO <n> · PIVOT <n> · NO-GO <n> · 합의도 <높음/보통/의견 분열>

판결 요지
- (이유 1)
- (이유 2)
- (이유 3)

가장 먼저 할 일: (판결문 실행 계획의 첫 2주 실험과 성공 기준)

모델별 배심원 평균: opus 64.2 · sonnet 61.0 · haiku 70.5   ← 배심원 모델이 섞였을 때만
기록: <CASE_DIR>/08-판결문.md · <CASE_DIR>/재판기록.md
```

3. 마지막에 한 줄로 다음 선택지를 제안한다: 아이디어를 보완해 **재심**, 같은 사건을 **다른 모델 구성으로 재판**해 비교, (Artifact 도구가 있으면) 판결문을 **공유용 페이지**로 게시.

### 재심

사용자가 보완한 아이디어로 재심을 청구하면 새 사건 폴더를 만들고 사건번호 뒤에 `-재심1`, `-재심2`를 붙인다. `01-사건기록.md`의 "제출된 자료"에 전심 판결의 주문·최종 점수·이행 조건을 "전심 판결 요지"로 넣고, 무엇이 바뀌었는지를 적는다. 검사는 전심의 혐의가 해소됐는지부터 따진다.

## 서브에이전트를 쓸 수 없는 환경

Agent 도구가 없으면(예: 서브에이전트가 없는 채팅 환경) 역할별 모델 지정은 할 수 없다. 사용자에게 그렇게 알린 뒤, 같은 순서와 같은 파일 구조로 역할을 하나씩 직접 수행한다. 이때는 각 역할을 쓰기 전에 앞 역할의 입장을 잊고 roles.md의 해당 섹션만 따른다. 배심원은 5명으로 줄인다.
